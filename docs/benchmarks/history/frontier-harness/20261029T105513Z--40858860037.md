- 命令里也没有 `python -u`、`PYTHONUNBUFFERED`、`faulthandler`（基线用过 1 次 `faulthandler`，本轮 0 次）。

原因很直接：**它这一轮没有崩溃**。提示描述的是「崩溃如何被上报」，而它选择了不需要崩溃的路线，所以那句提示没有用武之地。

按清单预先写定的判读规则，这落在规则二与规则三之间的一个新情形——行为变了，但不是被那句提示改变的。规则原本假设它仍会走 `ctypes` 直调路线，实际它一开始就换了路线，所以**规则二（提示改变行为）不成立**，也**不是规则三（提示未生效且路线照旧）**，因为路线本身变了。

## 三、路线为什么变了：一次未被分离的策略分叉

本轮它在第 2 次调用就选定「自己实现 C 版」，与基线直接调 Debian LAPACK 是**不同的策略分支**。可能的来源有两个，本臂无法区分：

1. **运行间方差**：该格在历史 27 次尝试里路线五花八门，其中 2026-09-30 那次通过（50 次调用）。
2. **请求前缀变化**：描述文本是请求前缀的一部分，`shell` 描述从约 1,000 字节涨到 1,294 字节，`exec` 也变长；前缀不同会改变采样轨迹。注意其中一句是 `exec` 现在会说明「直接启动的进程被信号杀死会返回 `signaled`」——但那句话与「选 C 而不是 ctypes」没有可追溯的因果，本轮文本里也没有引用。

**诚实结论**：本轮观察到的路线改变，不能归因于本次文本改动；单次尝试也不足以把「提示效果」与「该格自身的运行方差」分开。这正是清单 `knownRisks.singleAttempt` 预声明的局限。

## 四、真正卡住这格的是预算，不是提示

两轮都精确耗尽 900 s。本轮 10 次调用里，两次超长（350 s + 274 s = 624 s，占 71%）都花在**写大段 C 代码于推理中**。也就是说：

- 它想的方案（Hessenberg + Francis 双位移 QR + 复数反迭代，编译一次、ctypes 调用）是这个问题的**正确**高性能解法方向；
- 但「从零写一个数值库 + 编译 + 调对 + 跑基准到快过 numpy」在 900 s 内做不完；
- 基线那轮把预算花在诊断死循环上，本轮花在实现上，两轮都没走到「测速验收」。

**所以这格是一个预算墙格子，而不是一个提示可救的格子。** 这与前面第五节 5.3 的判断一致，并且现在有了第二条独立证据：换掉提示文本、换掉路线，结论不动。
